Add a canonical tool execution coordinator with batch-wide argument preflight, conservative host-owned concurrency metadata, cancellation-aware dispatch, and fail-closed unknown write outcomes. Route model, deferred, and Code Mode tool execution through the coordinator.

Persist canonical `tool.prepared`, `tool.attempt_started`, and `tool.attempt_completed` lifecycle events before and around dispatch. Include durable execution identity, argument fingerprints, capability snapshots, nested parent/root lineage, post-dispatch cancellation classification, and explicit required-action preflight resolution in replayable turn and streaming event schemas.


Register host-owned execution capabilities through remote connector resolution and canonical local tool definitions, enabling explicit parallel-safe and resource-scoped scheduling while preserving conservative defaults. Add bounded fresh-attempt retries for retry-safe reads, and classify persisted prepared, started, and completed attempts during restart so ambiguous writes become model-visible reconciliation blockers instead of blind retry instructions.

Add durable canonical approval identity. Introduce Zod-owned `ApprovalPolicyIdentity` and `ApprovalBinding` contracts and a stable selector policy version derived from the normalized effective enable/disable/preload/require-approval selectors. `ToolSet` exposes a synchronous policy identity and snapshots it into `InternalToolCallInfo` when enriching assistant calls; `tool.approval_required` refs carry the durable binding (version, thread id, origin model-message id, tool-call id, stable tool-set id, original tool name, canonical decoded-argument fingerprint, and policy id/version). Public approval input may echo the binding, but old clients stay compatible: the exact expected binding is computed and persisted from the durable pending call when absent, and a supplied mismatch is rejected. Approval scanning retains decision and binding together, and `executeToolCalls` threads both to the coordinator. The `ToolExecutionCoordinator` recomputes the expected binding against live tool-set identity and current policy after strict decode, and fails closed (failure class `policy`) before preflight/dispatch on a missing or mismatched allow binding; denial stays terminal even without a binding, and nested/Code Mode dispatch inherits the approved parent. Canonical argument hashing is factored into one shared owner used by both the lifecycle and approval paths. Legacy durable assistant calls without a policy snapshot may bind against current policy only when presenting or accepting a fresh human approval; a legacy persisted allow decision without a binding fails closed.

Add live coordinator input-schema validation. `ToolSet` remains the owner of discovered MCP input schemas and now exposes an optional synchronous `getToolInputSchema(toolName)` on `IToolSet`, backed by a per-instance cache populated from its own `listTools`/source results (instance-isolated, no policy bleed); `LocalToolMCP` returns its canonical `defineTool`-generated schema, so DeferredTool's root `call_tool` validates against its wrapper schema while a nested underlying invocation validates against the underlying tool's schema. A new Zod-owned `core/mcp/inputSchemaValidator` module validates a decoded object recursively against a discovered schema, emitting deterministic, bounded, JSON-pointer-like field-level violations (capped count and depth). It supports `type` (including type arrays), `required`, `properties`, `additionalProperties` (`false`/schema), `enum`, `const`, array `items`/`minItems`/`maxItems`, string `minLength`/`maxLength`/`pattern`, numeric `minimum`/`maximum`/exclusive bounds, `nullable`, and boolean schemas; unknown keywords/dialects are ignored rather than causing false rejection, malformed/unavailable schemas skip safely, and known violations fail closed. The validator never throws on arbitrary schema/value input. The `ToolExecutionCoordinator.prepareBatch` runs validation after strict decode and the known-tool check and before approval, preflight, and dispatch: a violation becomes a terminal invocation with failure class `validation`, error code `input_schema_validation_failed`, and bounded structured `violations`/`truncated`, so it never reaches policy, preflight, or the dispatch leaf while still recording complete `tool.prepared`/`tool.attempt_completed` lifecycle events.

Add live, restart-safe no-progress enforcement. Introduce a Zod-owned `core/mcp/NoProgressController` with validated config (`enabled` plus strictly ordered `reminder < replan < stop` thresholds, defaults 2/3/5, and a bounded recent-history limit) and a durable, evidence-free state schema. The controller is fixed-core and default-on in every `AgentThread`: `AgentDefinition.noProgress` may pass `false` to disable it or a validated partial threshold/history override, but safe defaults always apply. Durable state rides the existing `capability_state` snapshot/event path under the reserved key `tfy.no_progress` — no second store — so it lands in snapshots/events and rehydrates on the next turn/restart (a malformed or version-mismatched value fails safe to a fresh state). After each completed ordinary model tool batch in `stepToolResponse`, the controller observes only bounded hashes: an order-independent action signature over stable tool-set id, original tool name, and the shared canonical argument fingerprint (independent of tool-call id/order), and an outcome signature over normalized result content / failure — no raw arguments or output are stored. The first failure counts; a subsequent different failed alternative neither resets nor increments; an exact or cosmetically-equivalent action with the same outcome increments; a new successful action or a changed successful outcome resets the counter and opens a new progress epoch. At `reminder`/`replan` the thread injects an explicit tfy-internal ephemeral guidance message before the next LLM call (never persisted to durable context) demanding a changed strategy and concrete new evidence; at `stop` it terminates through the existing error-event path with a bounded structured message before another LLM/tool dispatch, and only at the `llm-call-required` boundary — never while waiting on approval, a client-side tool, or auth. State is persisted immediately after each observation via the `CAPABILITY_STATE` event and mirrored into the local snapshot. `AgentThreadMetrics` gains optional `total_no_progress_reminders`/`_replans`/`_stops` counters with aggregate helper wiring. No assertions escape, no raw evidence enters state, and call-result cardinality is unchanged.
